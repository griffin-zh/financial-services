# 01 · 项目全景与定位

> 读完本章你会知道:这个仓库到底是什么、面向谁、交付成什么、为什么"没有真实交易引擎",以及它与旁边的 `financial-product/` 是什么关系。

## 1.1 它是什么

`financial-services` 是 **Anthropic 官方的「Claude for Financial Services」参考资产仓库**。它把金融服务行业(FSI)最常见的工作流,封装成可以直接安装、也可以托管部署的 Claude 能力包。

用一句权威定义(见 [README.md:1-5](../README.md#L1-L5)):

> Reference agents, skills, and data connectors for the financial-services workflows we see most — investment banking, equity research, private equity, and wealth management.

关键词是 **reference(参考模板)**。它不是成品软件,而是"起点":你 fork 下来,按自己公司的术语、流程、数据源去调,然后用。

## 1.2 它不是什么

这是理解全仓最重要的一点。它**不是**传统的可运行金融应用:

- ❌ 没有数据库表 / ORM / 迁移脚本
- ❌ 没有 REST / gRPC / GraphQL controller
- ❌ 没有交易、清算、支付、风控引擎
- ✅ 绝大部分是 **Markdown(系统提示词 / skill / command)+ JSON/YAML(manifest)**
- ✅ 唯一会真正运行的代码,是 `china-market` 的 A 股数据 MCP 服务(Python)

[README.md:99](../README.md#L99) 一句话点破本质:

> Everything is file-based — markdown and JSON, no build step.

**没有 build step** 意味着:改一个 `.md`,能力就变了,不需要编译。你的"开发"主要是写提示词和 manifest,并遵守仓库的校验 / 同步 / 版本纪律(见 [03](./03-核心设计理念.md) 与 [07](./07-工程化与工具链.md))。

## 1.3 文件构成:量化看清"真实代码只有一处"

| 类型 | 数量级 | 承载什么 |
|---|---|---|
| `.md` | ~280 | 系统提示词、SKILL、command、README、投研产出 |
| `.json` | ~44 | marketplace.json、plugin.json、.mcp.json、steering-examples |
| `.yaml` | ~41 | managed-agent 的 agent.yaml、subagents/*.yaml、config.yaml |
| `.py` | ~24 | **仅** china-market MCP(~1100 行)+ `scripts/` 工具链(~790 行) |

结论:**当你想"读代码"时,几乎只有 `china-market` 值得逐行读**(见 [06](./06-china-market代码走读.md));其余部分你读的是"自然语言定义的业务流程",而不是可执行逻辑。

## 1.4 面向谁:五个 FSI 垂直

仓库按金融业务线组织能力(见 [README.md:101-115](../README.md#L101-L115)):

| 垂直 | 面向的工作 |
|---|---|
| **financial-analysis**(核心) | DCF、comps、LBO、三表模型、deck QC、Excel 审计——**所有数据连接器都在这里** |
| **investment-banking** | CIM、teaser、buyer list、merger model、交易跟踪 |
| **equity-research** | 财报点评、首次覆盖、模型更新、投资论点跟踪 |
| **private-equity** | 项目溯源、尽调清单、IC memo、投后监控 |
| **wealth-management** | 客户 review、理财规划、再平衡、税损收割 |
| **fund-admin** / **operations** | GL 对账、accrual、NAV tie-out;KYC 文档解析 |

## 1.5 交付成两种形态(一源两包装)

同一份能力,[README.md:5](../README.md#L5) 明确说"两种方式、同一个源":

1. **Cowork / Claude Code 插件**——个人在 IDE / Cowork 里安装,skill 自动触发,slash command 随手可用(`/comps`、`/dcf`、`/earnings`……)。
2. **Claude Managed Agent(API 部署)**——通过 `/v1/agents` 部署到你自己的工作流引擎背后,headless 运行。

两者共享**同一份系统提示词**。这个"一源两包装"是全仓的骨架,详见 [03](./03-核心设计理念.md)。

## 1.6 为什么"没有真实交易引擎"——重要的产品边界

[README.md:7-8](../README.md#L7-L8) 的免责声明是理解全仓设计的关键:

> 这些 agent 起草分析师工作产物(模型、备忘录、研究笔记、对账),供合格专业人士复核。它们**不做投资建议、不执行交易、不绑定风险、不过账、不审批开户**;每个输出都停在待人签字这一步。

所以"仓库里没有交易 / 过账 / 审批代码"**不是缺失,而是有意为之**。演进时你应守住同一条线:让 agent 产"待复核的草稿",把"执行 / 签字"留给人和下游系统。这条边界也体现在 Managed Agent 的安全隔离设计里(见 [05](./05-Managed-Agent与编排.md))。

## 1.8 与下游 `financial-product/` 的关系

在 `/home/griffin/financial/` 下,`financial-services/` 旁边并列着另一个**不同的**项目 `financial-product/`(它有 `api-server/`、`webui/`、`docker-compose.yml`,是真正的前后端产品)。两者的关系是**上游模板 vs 下游消费方**:

- `financial-services` 是 china-market MCP 服务的**代码单一源**,由 CI 打成镜像发布到 GHCR;
- `financial-product` 只是**拉这个镜像来用**(其 `docker-compose.yml` 里的 `mcp-china-market` 服务),不维护拷贝。

所以:**改 A 股数据能力,永远改 `financial-services/plugins/partner-built/china-market/mcp_server/`,不要去下游改**(见 [CLAUDE.md:66](../CLAUDE.md#L66))。
